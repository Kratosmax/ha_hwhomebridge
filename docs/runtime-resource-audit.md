## 已部署的插座优化复核

- 四张卡使用同一 `socket_runtime`，餐桌特殊配置已移除。
- 功率事件只提交power，开关事件只提交switch；仅属性变化不重报。
- 电量事件只检查对应SN；仍有每分钟电量检查，防止事件被锁跳过后永久漏报。
- 无倒计时任务时不派发每秒工作线程；每秒轻量回调仍保留倒计时精度。
- 周期上报省略此前成功的delay，失败则重试；倒计时操作照常上报。
- 四插座、其中两个带功率的静态周期调用由9次/分钟降为6次/分钟；不包含实际事件及新增电量。
- 安装新插座监听前清理同一列表内旧监听；这不能代替集成卸载清理。
- 顺序调整曾引发用户确认的显示翻转，已撤回。不要再次将顺序对照当作修复。

## 尚未修正的明确问题

1. **卸载清理不完整**：`__init__.async_unload_entry` 只置空SDK回调，没有注销 `socket_test_listeners`，也没有停止扩展启动任务。可能在集成卸载后继续轮询或上报。需要与重新加载流程一起设计和测试；只取消监听会使现有重新加载流程无法恢复它们。
2. **队列没有容量限制**：`ThreadPoolExecutor` 直接接收每次状态请求，长期SDK锁阻塞时可积压。应单独处理状态消息合并与注册/控制消息的顺序语义，不能简单丢弃任务。当前未测到长期阻塞情况下的实际内存增量。
3. **启动固定等待过长**：空调60+60秒、温湿度60秒、门磁60秒、插座75秒串联，固定等待累计至少315秒，另有连接、轮询和验证开销。缩短需要真实云端就绪证据，不能直接删除等待；尚未证明这就是餐桌初始显示关闭的原因。
4. **既有设备仍发新增注册**：空调启动固定发status3再status1；运行版门磁启动也重复新增。温湿度已有新旧区分。可评估把新设备与已有设备注册统一，但状态3是否必要须按品类验证，当前不改云绑定。
5. **事件上报仍有可精简空间**：空调任一实体状态/属性变化发完整快照，温湿度任一测量更新发两项读数。应比较实际上报值并处理失败重试、离线恢复、重连重同步，不能直接永久缓存成功值。
6. **重试只代表本地提交结果**：门磁缓存提交值，失败时清除；没有独立周期重试，源无后续事件时失败可能直到下一次重同步才恢复。失败回调与新提交并发时也需要防止旧回调清掉新缓存。

## 内存与存储边界

- 空调、温湿度、门磁、插座诊断分别使用有限长度deque；不是无限追加内存列表。
- 插座耗电只提交新增Wh，成功后持久化基线；不能每分钟重复累计总量。
- 注册探针会生成新文件，安装探针亦保留结果；目前没有自动保留数量策略。未测量实际目录大小，不宣称已发生磁盘耗尽。
- 开发机仓库与HA运行目录有意存在差异，尤其燃气失败实验不能整目录部署。
