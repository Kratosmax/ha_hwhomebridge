# 插座品类与定时：离线开发记录

## 原生服务表 ABI 修正（2026-10-18，手机验收通过）

SDK 的服务表消费者按 64 项结构读取：类型数组占 `64 * 32 = 0x800`
字节，服务 ID 紧随其后，整条记录大小为 `0x1800`。固定 amd64 库中
`0x9f540` 的读取代码使用 ID 偏移 `0x800`；SDK 批量调用方为每台分配
`0x1800` 字节。厂商回调 `0xe270` 和 `0xe460` 却按 20 项输出，ID
偏移为 `0x280`，批量步长为 `0x780`。这是接口布局不匹配，不能用
厂商旧头文件中的默认 20 项替代 SDK 二进制的实际布局。

构建器只修正三个输出布局指令：单台 ID 偏移、批量 ID 偏移、批量输出
步长；内部每品类的 20 项存储表及其读取偏移保持原样。候选不新增品类、
设备分支、轮询或上报；其他 7 槽产品元数据保持原值。

隔离 Linux 进程对照测试发现：旧库按 SDK 布局单台读取的 10 个 ID 均为空，
批量读取还会混入下一台的字段；修正后的单台、连续三台批量读取均正确。
常规原生探针现增加所有 8 槽的双台服务表比较，并由计划明确选择候选
64 项 ABI，保留旧基底的 20 项布局用于对照。探针不启动 SDK main，
不读取绑定、注册设备或连接网络。

部署后，用户确认餐桌详情首次进入及返回主页重新进入，两次都立即显示开启，
本次复现步骤验收通过。后台确认四插座在线、各品类设备身份不变，连续
两轮上报正常，27 次队列采样均为零。此次结果不等于已经覆盖长时间运行、
离线重连等情形，也不证明排除了所有其他因素。私有部署、
隔离结果和回滚清单保存在项目 `temp/socket-service-abi/`，不得推送。

餐桌排插已通过单设备实机验收。用户随后授权删除原卡片并迁移其他插座；当前扩展到本地选择的各插座总开关。个人实体选择、名称与旧SN只在本地配置，不写入源码。

已核对两个真实的插座产品：[105M](https://smarthome-drcn.dbankcdn.com/device/guide/105M/105M.json) 和 [124U](https://smarthome-drcn.dbankcdn.com/device/guide/124U/124U.json)，均为01D插座品类。105M为欧瑞博S30c，124U为正泰插座；均具备switch、timer、delay。两者的字段并不完全相同，不能混用服务表。

124U官方H5 `h5_001/static/js/app.6a73afde048bdac512d2.js` 中，`setDelay`、`delDelay` 和定时编辑代码可核实：

- 开关为 `switch.on`，0关、1开。
- 倒计时为 `delay.action`：1创建、0修改、2删除。每只插座最多一项，修改和删除携带已有id。
- `delay.delay` 是对象数组；`sid` 为 `switch`、`para` 为 `on`。
- `start` 是开，`end` 是关，值为 `yyyyMMddTHHmmssZ` UTC截止时间。不是秒数、分钟数或相对时长。
- 周定时不是用户需求，不开发；对应未支持指令继续拒绝。

`socket_delay.py` 实现独立的倒计时解析与保存逻辑：

1. 拒绝同时开关、无效时间、过期创建和无法确认的字段，不猜测设备动作。
2. 原子保存任务，修改/取消按id匹配，提供卡片所需的数量与列表回读。
3. `CountdownStore.tick` 接收执行回调，在截止后尝试一次。任务先落盘移除再执行，执行失败不反复开关；落盘后执行前进程中断可能丢失本次动作，不宣称保证执行。
4. 重启时清理已经错过的任务，不补发一次突然开关；未来任务保留。

测试使用模拟开关和项目temp目录，覆盖时区、开关方向、编辑、取消、持久化、重启过期和执行失败。`socket_runtime.py` 将其接到单个测试实体、HA秒级调度与SDK查询/上报；只有智慧生活真实下发开关或倒计时命令才执行对应动作，启动和注册不切换实体。读写任务文件放到执行器线程，HA事件循环内串行处理修改和到时任务。只接受主开关及倒计时指令，周定时和其他未实现控制返回拒绝。

`tools/build_socket_candidate.py --profile <官方124U.json>` 从固定哈希基底生成项目temp中的候选及验证计划，不写活动库。`socket_validate_metadata` 服务只读取固定检测目录，在独立进程、无网络命名空间内检查全部8槽的单设备/批量元数据；不调用SDK main、不读取绑定、不注册设备。2026-10-18本机验证通过，槽1至7与已验收基底完全一致，仅未使用的槽0改为124U。此结果不能代替云端注册和手机验收。

本地 `socket_test_enabled` 默认关闭，启用需指定 `socket_test_entity`、已完成的元数据计划与对应候选库。启动时还会重新做一次隔离检测，失败保持已有库。`socket_test_registered` 只在手机确认新卡片正常后设为true，使后续重启仅上报在线；未确认时保持测试状态，不擅自标为完成。

批量迁移使用本地 `socket_entities` 列表：每项选择一个entity_id，可指定name、registered及对应old_sn。每个实体沿用独立、固定的新插座SN；同一存储按SN区分倒计时，命令、修改和取消都不会跨插座。不可用设备跳过。新卡创建HA桥接条目并设置显示名称，原始HA设备和实体不删除。

`socket_retire_legacy` 仅接受显式old_sns列表，目标必须在本地迁移清单、仍为008旧品类、映射到同一总开关，且替代插座已在线、switch和delay上报都返回0。检查通过才持久保存旧SN排除记录、发送仅该旧SN的删除状态，并移除其HA桥接条目；不移除原始设备或实体。未来注册包装器拦截已排除旧SN的上线请求，避免旧卡重生。SDK删除返回0仍需手机确认云端旧卡消失，不将它当作云端删除回执。

本轮迁移已执行：4个新插座上报正常，对应4个旧卡删除调用成功、排除记录持久化、旧桥接条目移除；原始HA设备保留，迁移前后总开关均为on，未做物理切换。31项单测通过。手机端批量迁移验收仍待确认，证据在项目temp/socket-migration。

## 功率、电量和房间继承

`chuangmi.plug.212a01` 的MIoT属性5.6是实际功率，属性5.7是过功率阈值，不得当成功率。属性名称虽然写有0.01W，但本次实机HA读数180W与用户米家180～190W一致，应直接使用HA的W数值，本机power_scale为1；之前额外乘0.01导致错误显示2W，已撤销。不得仅凭属性描述重复换算；其他设备若实际输出原始百分之一瓦，仍需独立验证其缩放。124U的power.current使用整数瓦，按整瓦四舍五入。

属性5.1在HA中已转换为kWh，状态类别为total_increasing。官方124U H5的用电量图读取云端`consumption.consumption`统计sum后除以1000。因此发送新增Wh，不能重复发送累计kWh，也不能把接入前的累计量伪装成今日新增。首次发0建立统计，后续只发送计数器新增部分，SDK成功后持久保存基线；计数器复位按total_increasing语义处理，单次超过1000Wh的差额分次上报。历史从实际接入后开始，不移植源平台旧历史。`socket_meter.py`及测试覆盖换算、重复总量、重启、复位和上报余量。

桥接设备的HA区域继承源实体的area_id，源实体无区域时继承原设备。云端目标房间由本地room_name提供，不在公开源码存放家庭/房间身份；名称/房间回调只读填充元数据。补上HA区域不会自动修改已经保存的华为云端名称或房间。

`socket_recreate_metadata`准备了受限的云端卡片重建路径：仅接受现有014插座SN、显式confirm_recreate=true、无待执行倒计时；调用云端删除状态后以相同SN新增，期间暂停该卡的上报和控制接收。它不调用HA开关服务，但云端卡片删除会影响其场景关联/历史，因此必须取得用户针对新卡重建的明确授权。此前删除旧008卡的授权不能自动用于此操作。此入口尚未调用，不将预备代码当作云端名称和房间已经修好。
